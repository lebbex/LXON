Definition

A doodad is the compressed form of an object. It serves to organize values by !! keys.single ! single character keys !. It doesn't allow for duplicate keys.

Doodads are most commonly used for storing vectors, coordinates, rotations, or in general small objects where the keys don't require full words to be identifyable.

They are also used in events where all keys in an !! cont.obj ! object ! or !! cont.map ! map ! will definetely be of single character length.

Syntax

To write a doodad, when prompted for a value, you must use a non-existant declaration character. The simplest way of doing so is using any letter, uppercase or lowercase, and !! other.escape ! escaping ! other characters that may be declaration characters. You can escape them by prepending a backslash \ to the character.

The letter (or symbol) you chose will be your first key in the doodad. The key does not require a colon at the end. Any key in the doodad following the first key doesn't need to be !! other.escape ! escaped !, as the doodad was already declared and all keys are recognized as keys directly, except for the obvious ones like:

  • Newline \n
  • Carriage Return \r
  • Backslash \\
  • Tab \t (preferably)
  • Null Character \0 (represents an empty character, which can also be a key, the same way you can have empty keys in !! cont.obj ! objects ! or !! cont.map ! maps ! by typing a colon directly)

After writing a key, write the !! val ! value ! properly, ensuring to properly terminate it before proceeding to the next key. Some values, such as !! val.text.full ! full strings ! cannot be terminated on the same line and require a newline altogether. The most reliable way of terminating a value is with a newline, which is supported for all value types.

Here are examples of doodads written on a single line (same movies listed in the !! cont.obj.syntax ! object's syntax example !): 

{
coordinate: x2391 y.3298 z-4234

movie1: t`Jacob's Ladder` y1990 d"Adrian Lyne

movie2: t`The Shining` r&1980-5-23

Multiline

As apparent in the example above, writing a doodad on a single line sometimes makes it hard to read. It is at the developper's discretion when they chose to represent doodads on multiple lines or on a single line, however it is wise to know to write doodads on multiple lines if necessary.

When writing a key/value pair on a newline, simply ensure to add 1 additionnal indentation compared to the line preceding it. Indentation MUST use tab characters, space characters aren't taken into consideration for indentation and are instead appended at the start of the key.

Here are examples of doodads written with multiline taken into account: 

a t"Acid Rap
	a "Chance The Rapper
	r &16-5-27

	b t "Acid Rain
		l &T0:3:36

c x0 y0
	z0

r y0
	p0 r0

Termination

Doodads are mainly terminated when the next line doesn't have the required indentation level. This is the most common way to terminate doodads.

Here are examples of indentation terminated objects: 

{
doo1: k"value
doo2:
	k"value

Rarely, usually only when writing a LXON data inline (all on one line), the indentation termination is impossible to achieve. This is because the next key or value external to the doodad isn't on a newline, but on the same line following the doodad.

In this scenerio, you should use the doodad termination symbol, a vertical bar / pipe |.

Here are examples of ways to terminate doodads using the termination symbol: 

{
doo1: i4 | doo2: i5 |
doo3: n3 | doo4: n4
doo5:
	k`value` |

Empty Doodads

Doodads cannot be empty, as their declaration character is also their first key. There is no purpose to supporting empty doodads, as doodads parse into objects with single character keys, and objects with single character keys parse into doodads. Therefore, to write an empty doodad, you must write an !! cont.obj.empty ! empty object !.

Standards

Doodads are often used to represent complex yet standard value with with determined keys, such as coordinates, rotations and vectors. There are standard ways of representing these values through doodads, although it is not a strict requirement nor an enforcement of a single meaning for a selection of keys.

Here are the standard ways of representing those complex values (the keys and their order):

  • Vectors and Coordinates:
    • 2D Coordinates (Vector2) xy
    • 3D Coordinates (Vector3) xyz
    • 4D Coordinates (Vector4) xyzw
    • 4D Physics Vector (time + coordinates) txyz
    • Spherical Coordinates rtp
    • 2D Geospatial Location (lat / long) lg
    • 3D Geospatial Location (lat / long / alt) lga
    • 2D Texture Coordinates uv
    • 3D Texture Coordinates uvw
  • Rotations:
    • Euler Rotation ypr
    • Quaternion Rotation wxyz *Distinguished from 4D Coordinates
    • Axis-Angle Rotation xyza
  • Dimensions:
    • 2D Scale (width / height) wh
    • 3D Scale (width / height / depth) whd
  • Color:
    • red / green / blue / alpha (opacity) rgba, although it's always better to use !! val.col.prec.float ! infinite precision color ! representation instead.
    • red / green / blue rgb
    • hue / saturation / value (brightness) hsv
